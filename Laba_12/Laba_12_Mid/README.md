# ЛР №12 — Вариант 8 (средний): Система двух ролей student / teacher

**Условие:** для разных ролей доступны разные страницы, роль проверяет сервер.

**Как сделано:** серверная сессия в cookie `sid` (HttpOnly). Роль пользователя хранится на сервере, клиент не может её подменить. Маршруты преподавателя защищены middleware `requireRole('teacher')`. Студент видит вкладки преподавателя с замком: они не скрыты специально, чтобы показать, что при нажатии сервер ответит **403**. Скрытая кнопка сама по себе не защищает данные.

**Творческое задание:** журнал аудита событий безопасности: входы, ошибки входа, выходы, отказы в доступе, истекшие сессии. Записывается время, логин, IP и подробности. Журнал видит только преподаватель (вкладка «Аудит входов»). С ним можно заметить подбор пароля или попытки студента открыть чужие данные.

## Запуск
```bash
npm install
npm start            # http://localhost:3002, сессия живёт 15 минут
npm run start:short  # сессия живёт 30 секунд — для проверки истечения
```

Тестовые учётные записи (не реальные данные):

| Логин | Пароль | Роль |
|---|---|---|
| `aliya` | `Student#12` | student (ID 1) |
| `daniyar` | `Student#12` | student (ID 2) |
| `ivanova` | `Teacher#12` | teacher |

## Роли и доступ
| Ресурс | student | teacher | Кто проверяет |
|---|---|---|---|
| `GET /api/students/:id/grades` | только свой ID | любой | маршрут: сравнение ID с сессией |
| `GET /api/journal` | 403 | ✓ | `requireRole('teacher')` |
| `POST /api/journal` (поставить оценку) | 403 | ✓ | `requireRole('teacher')` |
| `GET /api/audit` | 403 | ✓ | `requireRole('teacher')` |

## Схема
```
POST /api/login ──▶ 400 / 401 / 200 + cookie sid
                         │
запрос к API ──▶ requireAuth ── нет сессии / истекла ──▶ 401 (→ экран входа)
                         │
                   requireRole ── роль не подходит ──▶ 403 + запись в аудит
                         │
                    данные 200
POST /api/logout ──▶ сессия удалена на сервере, cookie очищена, запись в аудит
```

## Меры безопасности
- Роль берётся из сессии на сервере, а не из запроса или интерфейса.
- Каждый защищённый маршрут проверяется отдельно: `requireAuth` → `requireRole` / проверка владельца.
- Пароли — хеши scrypt; одинаковый ответ на неверный логин и пароль.
- Cookie `HttpOnly` + `SameSite=Strict`, `Secure` в продакшене.
- Журнал аудита фиксирует попытки входа и отказы в доступе.
- Вывод данных через `textContent` и заголовок CSP — защита от XSS.
